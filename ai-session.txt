● Overview

  This is a small TypeScript coding exercise: a solver for 4x4 tic-tac-toe.
  There's one commit and two source files.

  - src/tic-tac-toe.ts: the TicTacToe class. You pass two player names and a 4x4
    board of 1 | 2 | null.
    - The constructor checks that the move counts make sense (player 1 has the
      same number of moves as player 2, or one more).
    - checkWinner() builds every winning line (4 columns, 4 rows, 2 diagonals,
      the four corners, and nine 2x2 boxes). It returns the winner's name or
      null, and throws if both players have a winning line.
    - anyMovesLeft() and isGameOver() are simple checks built on top of that.
  - src/tic-tac-toe.test.ts: Vitest tests covering each win type, invalid move
    counts, and both players winning at once. All 30 tests pass.
  - Tooling: the only dependency is vitest. There's no tsconfig.json and no
    typescript package.

  Issues

  Bugs and edge cases
  1. An empty player name breaks isGameOver() (tic-tac-toe.ts:135). The check if
     (this.checkWinner()) treats the result as true or false, so if the
     winner's name is "" it counts as no winner. It should be !== null.
  2. Two players with the same name hide a double win. The check for both
     players winning compares names (tic-tac-toe.ts:105,111), so new 
     TicTacToe("X", "X", ...) never throws. Comparing the cell values 1/2 would
     avoid this, and so would rejecting duplicate names.
  3. The board's shape is never checked. A board smaller than 4x4 crashes with a
     TypeError on g[3][3], and a wider or uneven board fails at
     verticals[col].push. The constructor should reject anything that isn't 4x4.
  4. Some impossible boards get through. "Both players won" is only caught when
     checkWinner() is called, not in the constructor. The move counts also
     aren't compared with who won: if player 2 won, the counts must be equal,
     and if player 1 won, player 1 must have exactly one more move.
  5. The class holds on to the caller's array without copying it. If the caller
     changes the board after construction, the move-count check no longer holds.

  Code quality
  - The constructor's parameter is typed as (1 | 2 | null)[][] (:12) instead of
    the Cell type you already defined.
  - The 2x2 box code (:57-91) is 35 lines of hand-written branches. A short loop
    over the top-left corners (r, c) with r, c ∈ 0..2 would do the same job.
  - In checkWinner, forEach with a captured let winner works, but a for...of
    loop would read more simply.

  Tests and tooling
  - The parameterized tests type boards as number[][] and then cast them to
    Cell[][], which turns off type checking for the test data. Writing
    test.for<Cell[][]>([...]) would keep it.
  - Vitest removes the TypeScript types without checking them, and there's no
    tsc step, so type errors are never caught. Adding typescript and a
    tsconfig.json, plus tsc --noEmit in CI or as an npm script, would fix that.
  - npm test starts Vitest in watch mode. For a reviewer, vitest run is a better
    default.
  - No tests cover the edge cases above: wrong board size, empty or duplicate
    names, or a game that kept going after someone won.

  README
  - The code template is garbled: /*{{ params, if any }} _/): /_{{ return type 
    }}*/. Markdown seems to have turned some * characters into _.
  - The prompt asks for AI session transcripts if AI was used. None are in the
    repo, in case that applies to you.

  Overall, the core win detection is correct and well tested. The main fixes are
  #1 (a real bug) and #3 (missing input checks). I can make any of these
  changes if you'd like.

  Still open

  1. The board copy is only one level deep (tic-tac-toe.ts:12). [...game] copies
     the outer array, but the rows are still shared with the caller. If the
     caller changes a cell after construction (e.g. game[0][0] = 1), the
     instance sees it, and the board can end up invalid. A probe test confirmed
     this. Fix: this.game = game.map((row) => [...row]);
  2. Move counts aren't checked against who won (part 4b from before). This
     board is accepted even though O moved after X had already won:
  [1, 1, 1, 1]
  [2, _, 2, _]
  [_, 2, _, 2]
  [_, _, _, _]
     The rule to add: if player 1 won, they must have exactly one more move than
     player 2; if player 2 won, the counts must be equal.
